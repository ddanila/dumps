# Candidate PROM-enable latch timing

The candidate photo routes place U10 E2 through U5 at Am2901 I0/A1 and U11
E4 through U6 at I7/A0. Their electrical continuity and latch phase are
unmeasured. [The executable sweep](photo_enable_timing.py) varies both sampled
levels and all 256 initial Q values while running the real control PROMs for
512 instructions per case. The [saved result](results/photo-enable-timing.json)
contains the precise fixture, source hashes and startup outcomes.

| Latched E2 | Latched E4 | Q seeds reaching 38E | Visits to candidate 392 output across seeds | Same-phase U10/U11 read valid? |
| ---: | ---: | ---: | ---: | --- |
| 0 | 0 | 0 | 0 | No: E4 low |
| 0 | 1 | 32 | 0 | Yes |
| 1 | 0 | 0 | 0 | No: both enables wrong |
| 1 | 1 | 32 | 1248 | No: E2 high |

All 1024 bounded runs complete cleanly. The 32 active Q seeds are those
congruent to 5 modulo 8. The MMI 6381 [operating description](https://electronicsandbooks.com/edt/manual/Electronic%20Component%20Databook%20Datasheet/Brand/MMI%20Monolithic%20Memories%20Incorporated%20%28AMD%201987%29/Databook/1975%20MMI%20Semiconductors%20Data%20Applications%20c20130212%20%5B252%5D.pdf)
requires E2 low and E4 high for the corresponding read. Thus E2=1/E4=1 is a
**timing diagnostic**: the present fixture continues to use ordinary U10 data
bits even though the same-phase chip would be disabled. It is not a valid
physical execution unless a separately specified earlier read and latch hold
supplies those bits.

With Q=5, the script then feeds 128 bits generated by executing the real 8031
scrambler to the hypothesized D input at 38E. Under E2=0/E4=1, there are no
recurring ROM reads after the first bit; candidate 392 ALU Y is 11 on all 57
subsequent visits. Under diagnostic E2=1/E4=1, recurring reads at 389, 38A
and 38C settle at ROM addresses 100, 101 and 102, respectively, and 392 Y
settles to 6 after one 25. The 57 values at 396 are all 254. Neither case
shows an evolving carrier output or retained phase in this scoped run.

This sensitivity makes latch phase a useful next test, not a goal blocker.
Implement a two-phase or held-PROM-output candidate if the photo and logic
allow it; also continue testing other field mappings, controller interfaces
and output sites. Q=5, ROM gating, the D38E bit route and the physical output
connection remain assumptions. A clean run or a visit to 392 alone does not
meet the G2 transmitter or receiver acceptance criteria.

## Which E2-derived pin matters?

[A second executable screen](photo_e2_split.py) holds the PROM read phase at
E2=0/E4=1 and independently sets Am2901 I0 and A1 to 0 or 1. This deliberately
breaks the photo-inferred shared E2 route in three of four cases; it identifies
what the *model* is sensitive to, not a valid new board connection. Each case
consumes the same 128 controller-derived bits at 38E. The
[saved report](results/photo-e2-split.json) has source hashes and trace digests.

| I0 | A1 | Repeated reads after first bit | 392 ALU Y values | Photo shared route? |
| ---: | ---: | --- | --- | --- |
| 0 | 0 | None | 11 | Yes |
| 0 | 1 | None | 11 | No |
| 1 | 0 | 389→100, 38A→103, 38C→104 | 16, 26 | No |
| 1 | 1 | 389→100, 38A→101, 38C→102 | 6, 25 | No |

The addresses in this table are hexadecimal. I0 high, rather than A1 high,
opens the recurring ROM path in the tested fixture. A1 changes the ROM
addresses and ALU values once that path is open. The resulting reads and
values still settle; there is no demonstrated evolving carrier. The next
photo/timing hypothesis should therefore explain how I0 could be high while
valid U10 data is available, or try an alternative I0 route. Merely changing
A1 cannot rescue this Q=5 controller path.

## Capture-edge check

[A minimal four-state edge experiment](prom_enable_edge.py) uses the actual
U10 dump in the board engine, with its active-low E2 gate and an LS374-style
U5 capture edge. It gives the other U10 enables their asserted levels and,
generously, connects U10 D1–D7 directly to U5 D1–D7. The actual data-bit
permutation and E2-to-D0 route remain unverified. At address 004, U10's real
data byte is EC. The
[saved edge result](results/prom-enable-edge.json) is:

| Event order | U5 Q7–Q0 after event |
| --- | --- |
| Capture while E2 low | `11101100` |
| Raise E2, then capture | `ZZZZZZZ1` |
| Capture while E2 low, then raise E2 | `11101100` |
| Raise E2 and capture in one modeled event | `11101100` |

Here `Z` is a high-impedance data bit, not zero or a retained value. In the
last case the edge samples the old D inputs; the model has no propagation
delay or analog race behavior. Under this *simple* photo route, U5 cannot
capture both E2=1 at D0 and valid U10 data at D1–D7 on one edge. That makes
the earlier E2-high ROM path a stronger prompt to test a different I0 route
or a separately specified holding circuit, not a valid execution under the
current board topology. This edge check does not run the whole microprogram
or establish the physical output connection.
